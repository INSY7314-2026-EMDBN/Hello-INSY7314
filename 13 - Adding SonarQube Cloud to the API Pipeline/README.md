## Requirements

Your API pipeline already:

* installs the backend dependencies;
* runs ESLint;
* runs the Jest unit tests;
* clears the dedicated Atlas CI test database;
* builds the API Docker image;
* starts the containerised API; and
* executes the existing PulseVote RBAC Postman collection with Newman.

In this activity, we are extending it.

After this activity, your PulseVote backend will also:

* generate Jest code coverage during CI;
* send the backend source code and coverage information to SonarQube Cloud;
* display code-quality and security findings in SonarQube Cloud; and
* use the SonarQube Quality Gate as another pipeline check.

> Note: you may need to push your project to your own repo for this activity as Sonar permissions won't work on the organisation.

## 1. Create a SonarQube Cloud project

1. Go to SonarQube Cloud and sign in using GitHub.
2. Import your GitHub organisation/repository.
3. Select your PulseVote repository.
4. If SonarQube Cloud enables Automatic Analysis, turn it off for this project:

   Project → Administration → Analysis Method → Automatic Analysis → Off

   We are deliberately using CI-based analysis because the scan must happen inside our GitHub Actions pipeline and we want to supply the Jest coverage report.

5. Choose GitHub Actions as the analysis method.
6. Keep the SonarQube Cloud page open. You will need your:

   * organisation key;
   * project key; and
   * Sonar token.

Do not place the token directly in your code or workflow file.

## 2. Add the Sonar settings to GitHub

Open your PulseVote repository on GitHub and go to:

Settings → Secrets and variables → Actions

### Repository secrets

You should already have these secrets:

```text
MONGO_URI
JWT_SECRET
POSTMAN_TEST_PASSWORD
```

Under Secrets in the repo settings, add in the token supplied/generated by SonarQube Cloud as:

```text
SONAR_TOKEN
```

Also, under Secrets in the repo settings, add in the exact organisation key and project key shown by SonarQube Cloud under Project → Project → Project Information.

```text
SONAR_ORGANIZATION
SONAR_PROJECT_KEY
```

## 3. Generate Jest coverage

SonarQube Cloud can analyse our JavaScript source without Jest coverage, but adding the coverage report allows it to show which code was exercised by our unit tests.

In `pulsevote-backend/package.json`, add another test script:

```json
"scripts": {
  "start": "node server.js",
  "dev": "npx nodemon server.js",
  "test": "jest --passWithNoTests",
  "test:coverage": "jest --coverage --passWithNoTests",
  "lint": "eslint .",
  "db:clear": "node scripts/clearDatabase.js"
}
```

Test it locally from `pulsevote-backend`:

```bash
npm install
npm run test:coverage
```

A `coverage` directory should be generated.

You do not commit the generated coverage directory. Your existing `.gitignore`/lint configuration should continue to exclude generated coverage files.

## 4. Add the SonarQube project configuration

Create this file in the backend root:

```text
pulsevote-backend/sonar-project.properties
```

Add:

```properties
# SonarQube Cloud analysis settings for the PulseVote backend.
# The project key and organisation are supplied by GitHub Actions variables.

sonar.sources=.
sonar.tests=test
sonar.test.inclusions=test/**/*.test.js

sonar.exclusions=node_modules/**,coverage/**,postman/**,ssl/**
sonar.coverage.exclusions=test/**,scripts/**,server.js
sonar.javascript.lcov.reportPaths=coverage/lcov.info
sonar.sourceEncoding=UTF-8
```

Research each property before continuing.

In particular:

* `sonar.sources=.` tells SonarQube to analyse the backend project;
* `sonar.tests=test` identifies the Jest test directory;
* `sonar.exclusions` prevents generated or non-source files from being analysed as application source; and
* `sonar.javascript.lcov.reportPaths` points SonarQube to the coverage report generated by Jest.

We do not hard-code the SonarQube organisation or project key in this file. The pipeline supplies them from GitHub Actions variables.

## 5. Update the GitHub Actions pipeline

Open:

```text
.github/workflows/api-ci.yml
```

### 5.1 Fetch the complete Git history

Update the checkout step:

```yaml
- name: Check out repository
  uses: actions/checkout@v4
  with:
    fetch-depth: 0
```

SonarQube recommends disabling shallow clones because the additional Git history improves the relevance of the analysis.

### 5.2 Generate coverage instead of running the basic test command

Replace:

```yaml
- name: Run unit tests
  run: npm test
```

with:

```yaml
- name: Run unit tests with coverage
  run: npm run test:coverage
```

The tests themselves have not changed. We are simply asking Jest to produce the coverage report as part of the same test run.

### 5.3 Add the SonarQube Cloud scan

Immediately after the coverage step, add:

```yaml
- name: Analyse backend with SonarQube Cloud
  uses: SonarSource/sonarqube-scan-action@v8
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  with:
    projectBaseDir: pulsevote-backend
    args: >
      -Dsonar.organization=${{ secrets.SONAR_ORGANIZATION }}
      -Dsonar.projectKey=${{ secrets.SONAR_PROJECT_KEY }}
      -Dsonar.qualitygate.wait=true
```

Notice the important parts:

* `SONAR_TOKEN` comes from a GitHub **secret**;
* the organisation and project key come from GitHub **variables**;
* `projectBaseDir` points the scanner at `pulsevote-backend`, not the frontend; and
* `sonar.qualitygate.wait=true` makes the workflow wait for the Quality Gate result.

If the Quality Gate fails, the CI job should fail rather than continuing as though the code-quality check passed.

## 6. Complete workflow

Your complete `.github/workflows/api-ci.yml` should now be:

```yaml
name: API CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  api-ci:
    runs-on: ubuntu-latest

    defaults:
      run:
        working-directory: pulsevote-backend

    steps:
      - name: Check out repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
          cache-dependency-path: pulsevote-backend/package-lock.json

      - name: Install backend dependencies
        run: npm ci

      - name: Lint backend
        run: npm run lint

      - name: Run unit tests with coverage
        run: npm run test:coverage

      - name: Analyse backend with SonarQube Cloud
        uses: SonarSource/sonarqube-scan-action@v8
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
        with:
          projectBaseDir: pulsevote-backend
          args: >
            -Dsonar.organization=${{ secrets.SONAR_ORGANIZATION }}
            -Dsonar.projectKey=${{ secrets.SONAR_PROJECT_KEY }}
            -Dsonar.qualitygate.wait=true

      - name: Clear CI test database
        env:
          MONGO_URI: ${{ secrets.MONGO_URI }}
          ALLOW_DB_CLEAR: true
        run: npm run db:clear

      - name: Build API Docker image
        run: docker build -t pulsevote-api-ci .

      - name: Create Docker test network
        run: docker network create pulsevote-ci

      - name: Start containerised API
        run: |
          docker run -d \
            --name pulsevote-api \
            --network pulsevote-ci \
            -e PORT=5000 \
            -e USE_HTTPS=false \
            -e MONGO_URI="${{ secrets.MONGO_URI }}" \
            -e JWT_SECRET="${{ secrets.JWT_SECRET }}" \
            pulsevote-api-ci

      - name: Wait for API health check
        run: |
          for i in {1..30}; do
            STATUS=$(docker inspect --format='{{.State.Health.Status}}' pulsevote-api 2>/dev/null || echo starting)
            echo "API health status: $STATUS"
            if [ "$STATUS" = "healthy" ]; then
              exit 0
            fi
            if [ "$(docker inspect --format='{{.State.Status}}' pulsevote-api 2>/dev/null)" = "exited" ]; then
              docker logs pulsevote-api
              exit 1
            fi
            sleep 2
          done
          docker logs pulsevote-api
          exit 1

      - name: Run existing Postman collection with Newman
        env:
          POSTMAN_TEST_PASSWORD: ${{ secrets.POSTMAN_TEST_PASSWORD }}
        run: |
          docker run --rm \
            --network pulsevote-ci \
            -v "${{ github.workspace }}/pulsevote-backend/postman:/etc/newman" \
            postman/newman:alpine \
            run "/etc/newman/PulseVote RBAC Test.postman_collection.json" \
            --env-var PROTOCOL=http \
            --env-var HOST=pulsevote-api \
            --env-var PORT=5000 \
            --env-var ADMIN_PASSWORD="$POSTMAN_TEST_PASSWORD" \
            --env-var MANAGER_PASSWORD="$POSTMAN_TEST_PASSWORD" \
            --env-var USER_PASSWORD="$POSTMAN_TEST_PASSWORD" \
            --bail

      - name: Show API logs if the pipeline fails
        if: failure()
        run: docker logs pulsevote-api || true

      - name: Clean up Docker resources
        if: always()
        run: |
          docker rm -f pulsevote-api 2>/dev/null || true
          docker network rm pulsevote-ci 2>/dev/null || true
```

## 7. Push and inspect the pipeline

Commit and push your changes:

```bash
git add .
git commit -m "Add SonarQube Cloud analysis to API pipeline"
git push
```

Open:

**GitHub → Actions → API CI**

You should now see the additional stages for:

```text
Lint backend
       ↓
Unit tests + coverage
       ↓
SonarQube Cloud analysis / Quality Gate
       ↓
Clear CI database
       ↓
Docker build + API startup
       ↓
Newman RBAC tests
```

If SonarQube fails, do not simply remove the scan from the workflow. Read the error and determine whether the problem is:

* pipeline configuration;
* a missing Sonar token/variable;
* Automatic Analysis still being enabled; or
* an actual Quality Gate/code-quality problem.
